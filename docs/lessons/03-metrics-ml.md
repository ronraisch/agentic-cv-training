# 3 — evaluation ומודל קטן למסלולים

## מה נספר כזיהוי

IoU הוא שטח החיתוך חלקי שטח האיחוד. לשני ריבועים [0,0,10,10] ו־[5,0,15,10]
יש חיתוך 50 ואיחוד 150: IoU=1/3 בחוזה קואורדינטות רציף. תוספת +1 שמתאימה לחוזה
פיקסלים אחר משנה את התשובה. קובעים את החוזה לפני הבדיקה.
עבור class וסף IoU נתונים, ממיינים חיזויים לפי confidence ומשייכים כל GT לכל היותר
לחיזוי אחד לפי פרוטוקול מתועד. כפילות סביב אותו GT יוצרת FP, לא TP נוסף.
GT ללא חיזוי הוא FN. לדוגמה TP=3, FP=2, FN=1 נותן precision=3/5 ו־recall=3/4.
עמימות של class, ignored/crowd ו־GT חסר אינן נפתרות באמצעות בחירת threshold נוחה.

PR curve משנה confidence threshold. AP מסכם עקומה לפי פרוטוקול interpolation
מוגדר; אינו "precision בנקודה הטובה ביותר". AP50 שונה מממוצע AP במספר ספי IoU.
השוואת גלאים דורשת אותו evaluator ו־class map, לא מספרים משני dashboards שונים.
בסצנה בלי GT, חיזויים הם false positives; אם אין גם חיזויים יש לתעד denominator policy,
לא להכריז שרירותית על 100%. ספק שלא ענה אינו "אין זיהויים".

## יחידת הפיצול היא חלק מהניסוי

מסלול מכיל כמה פריימים מאותו אובייקט; שכפולו בכמה שורות לא יוצר דוגמאות עצמאיות.
מחלקים לפי video/scene/session או קבוצה מחמירה יותר שהחונך קובע. כל track מאותה
קבוצה נשאר באותו split. bootstrap, אם מבוצע, דוגם קבוצות ולא פריימים ומדווח את מספרן.
מעט קבוצות אינן תומכות בביטחון סטטיסטי גבוה גם אם יש אלפי שורות.

## XGBoost על tracks של YOLO

המשימה: לסווג track לקטגוריית יעד או true/false track לפי תיוג שסופק. אין להסיק תווית
"אמת" ישירות מ־YOLO class ואז להציג זאת כאמת חיצונית. יוצרים שורה אחת למסלול:
אורך עד זמן ההחלטה, סטטיסטיקות confidence, box area/aspect ratio, מהירות ושונות.
מגדירים יחידות וזמן. אם השירות מחליט אחרי 5 פריימים, מאפיין מאורך המסלול הסופי
מדליף עתיד. bbox pixels אינם מהירות במטרים בלי calibration.

XGBoost מחבר עצים שנלמדים בהדרגה כדי לשפר objective. עומק/כמות עצים ו־learning rate
משפיעים על התאמה ו־overfit; עץ חזק יותר אינו תמיד הכללה טובה יותר. מתחילים ב־majority
או threshold על mean confidence ומודל פשוט. בוחרים מעט configurations מראש,
early stopping ו־threshold רק על validation. test נפתח לאחר הקפאת בחירה.
מחשבים PR-AUC או מדד מתאים לחוסר איזון, confusion matrix ועלות טעויות רלוונטית;
accuracy לבדו יכול להסתיר אובדן כל הדוגמאות הנדירות. אין חובה להוסיף embeddings.

שומרים schema מאפיינים, סדר עמודות, missing-value policy, split/data hashes,
seed, parameters ו־artifact. מחשבים את אותה טבלת מאפיינים בשירות בלי labels או
עתיד. permutation importance תלויה בדאטה ובמתאמים; אינה הוכחה לסיבתיות.

## תרגיל "כיווננו אבל לא השתמשנו"

search מצא C=10 במודל SVM, אבל הקוד שמר SVC() חדש עם C ברירת מחדל.
לוג search מוצלח אינו ראיה שהמודל הנכון נבחר. קוראים את best estimator,
טוענים מהדיסק בסביבה חדשה, משווים parameters ותחזיות, ואז בודקים את המודל שה־API
טען. אותו כשל קיים כששומרים XGBoost עם מספר עצים שונה או checkpoint אחר.
רק chain מלאה מה־config לשירות תומכת בטענה "כך המודל המבצעי עובד".
