# 1 — שינוי קטן שאפשר להוכיח

## קוראים מערכת קיימת

מתחילים ב־entrypoint ובקלט אמיתי אחד. עוקבים מה־UI אל route, validation, service,
מודול החישוב, persistence והתגובה. שם קובץ או README עשויים להיות ישנים; רשמו
"כתוב בתיעוד" בנפרד מ"ראיתי קריאה" ו"הרצתי את המסלול". חיפוש שם פונקציה לבדו
אינו מוכיח מי מפעיל אותה. בנו טבלת caller→callee עם קישורים ל־commit הנוכחי.

לשינוי בנקודה יש גבול קטן: במצב point כלי הציור שומר x,y במרחב התמונה המקורית,
מציג marker ומאפשר undo. בשלב הראשון אין segmentation. כך אפשר לבדוק את ה־UI,
אירועי העכבר וחוזה השמירה בלי לתלות אותם במשקלים או GPU. שמירת prompt אינה מסכה
ואינה annotation מאושר. שדות אלה חייבים להישאר נפרדים.

## קואורדינטות הן חוזה

תמונה ברוחב 1000 וגובה 500 מוצגת ב־500×250, בלי padding. קליק (125,50) ביחס לפינה
השמאלית העליונה של התמונה המוצגת הוא (250,100) במקור. אם האלמנט מכיל letterbox,
מחסרים קודם offset של התמונה בתוך האלמנט ורק אז מחלקים ב־scale. קליק ב־padding
נדחה. zoom ו־pan משנים את הטרנספורמציה; שימוש ב־clientX ישירות ישלח נקודה שגויה.
השרת בודק גבולות וגם image revision כדי לא לעבד נקודה על תמונה אחרת בעלת אותו ID.

## לולאת העבודה עם אייג׳נט

לפני בקשת קוד כותבים כשל אחד, חוזה ודוגמת קבלה. נותנים paths ורק context רלוונטי.
מבקשים מהאייג׳נט לסמן הנחות שלא אומתו; אדם בודק את ה־diff והריצה. README, ADR,
skill ו־MCP הם דברים שונים: README מתאר כניסה, ADR מסביר החלטה, skill הוא נוהל
למשימה חוזרת ו־MCP חושף כלים. קובץ skill בתיקייה אינו מוכיח שהלקוח טען אותו:
בודקים trace, קריאת כלי מוצלחת ומקרה שגיאה. חוזרים ל־docs/AGENT_WORK.md להרחבה.

בדיקות צריכות להפריך את הפתרון, לא לשכפל אותו. עבור קליק, oracle עצמאי יכול להיות
תמונה עם מלבן ידוע, בדיקת zoom ושמירה/טעינה מחדש דרך המסלול האמיתי. לא מספיק שה־mock
מחזיר בדיוק את הקואורדינטות שהטסט עצמו נתן. מקרה רשת timeout צריך להציג שגיאה,
לא ליצור annotation ריק שנראה תקין. משמעות מחקרית יכולה להיהרס גם כשה־UI נראה טוב.

## תרגיל הסבר

ציירו מפת בקשה אחת, חשבו קואורדינטות עם offset, והסבירו איזה diff צר לא משנה
כלים אחרים. חונך משנה את גודל התצוגה ושואל מה התוצאה לפני ההרצה.
